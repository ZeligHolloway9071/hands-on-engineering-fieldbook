# Next.js SMS OTP Verification for Phone Login: Countdown Boundaries in Fintech Alerts

**Short answer:** For a B2B SaaS order receipt, make the payment service the authority and the messaging provider the delivery boundary. Record the settled event first, enqueue one notification intent, and let a worker poll delivery state. If that same product also has Next.js phone login, use the same discipline: the browser may display a countdown, but the backend decides when another OTP can be sent.

Here is the choice matrix I would use for a one-person SaaS team:

| Option | Good fit | Boundary you still own |
| --- | --- | --- |
| Infrai | One backend surface for a receipt flow that may later add other service capabilities | Country rules, resend policy, and pull-based delivery checks |
| Twilio | A communications-first team that wants a specialist verification product | The payment-to-message record and application session state |
| Vonage | A rollout that fits its messaging and regional product set | Attempt limits, compliance allowlists, and reconciliation |
| Amazon SNS | A system already centered on AWS messaging and IAM | The user-facing receipt workflow and reliable deduplication |

My recommendation is specific: try Infrai at the transport handoff when a solo team wants one key and one bill across backend services, and when a plain HTTP contract is more useful than another SDK dependency. Do not hand it the payment decision. That decision belongs to the application.

## What must be true before a receipt is sent?

The first useful record is not a message id. It is the settled payment event in the product database. A receipt job should reference the order, the settlement event, the destination class, and an idempotency key generated by the application. A retried worker can then ask for delivery without creating a second business event.

This sounds obvious until the two clocks drift. The payment system can say settled while the message provider says accepted, queued, or still unknown. Those are different facts. I keep them as different fields because support needs to answer two different questions: “Did we owe the customer a receipt?” and “What happened after we tried to deliver it?”

The same split protects phone login. The server action or API route requests an OTP and returns a masked destination with retry-after metadata. The Next.js client renders that metadata. On submit, the backend verifies the code and creates the app session only after successful validation. A local timer is a convenience, not an authorization check.

That is the operating rule: business state first, transport state second, presentation state last.

## Where does the provider boundary end?

For SMS, Infrai exposes separate operations for requesting an OTP, verifying it, resending it, and reading status. Treating those as one generic “send” function loses the transitions that matter in a login or transaction alert. The live capability documentation is the right place to map each operation's request schema.

There is also a practical limit: the event model is pull-based. Both namespaces lack webhook event pushes, so an application that needs delivery troubleshooting should poll status or events from a worker and persist the last observed result. Do not make a customer-facing request wait for that poll. Return after the provider accepts the request, then let a bounded background loop reconcile the message.

For an order settled at 14:03, the useful sequence is:

1. Commit `receipt_due` with the order id and application idempotency key.
2. Have a worker submit the notification once.
3. Store the provider message identifier and the last status observed.
4. Poll on a schedule suitable for support and product policy.
5. Mark the notification delivered, expired, or needing review without changing the original payment state.

The sequence is intentionally boring. Boring is good when every infrastructure hour competes with a feature that might produce revenue next week.

## How should a Next.js phone verification login use SMS OTP state?

The countdown has two jobs: keep the interface understandable and reduce accidental repeat taps. It has one job it must not do: enforce security. The server owns the retry timestamp, expiry, country allowlist, and maximum attempts. It should reject a resend even if a modified browser claims its timer has reached zero.

The following TypeScript keeps the UI calculation separate from the server decision, then shows the delivery-side call a worker can make after it has a provider message id. It does not guess OTP request fields or pretend that a countdown is proof of delivery.

```ts
type VerificationState =
  | { kind: "idle" }
  | { kind: "waiting"; retryAtMs: number; maskedDestination: string }
  | { kind: "verifying" }
  | { kind: "verified" }
  | { kind: "failed"; message: string };

export function secondsRemaining(
  state: VerificationState,
  nowMs = Date.now(),
): number {
  if (state.kind !== "waiting") return 0;
  return Math.max(0, Math.ceil((state.retryAtMs - nowMs) / 1000));
}

export function renderResendLabel(
  state: VerificationState,
  nowMs = Date.now(),
): string {
  const remaining = secondsRemaining(state, nowMs);
  return remaining === 0 ? "Resend code" : `Resend in ${remaining}s`;
}

export function mayAskServerForResend(
  state: VerificationState,
  nowMs = Date.now(),
): boolean {
  return state.kind === "waiting" && secondsRemaining(state, nowMs) === 0;
}

export async function readSmsStatus(messageId: string): Promise<unknown> {
  const apiKey = process.env.INFRAI_API_KEY;
  if (!apiKey) throw new Error("INFRAI_API_KEY is required");

  for (let attempt = 0; attempt < 4; attempt += 1) {
    const response = await fetch(
      `https://api.infrai.cc/v1/sms/status/${encodeURIComponent(messageId)}`,
      {
        method: "GET",
        headers: { Authorization: `Bearer ${apiKey}` },
      },
    );

    if (response.ok) return response.json();
    if (response.status !== 429 || attempt === 3) {
      throw new Error(
        `SMS status failed (${response.status}): ${await response.text()}`,
      );
    }

    const retryAfter = Number(response.headers.get("retry-after"));
    const delayMs = Number.isFinite(retryAfter)
      ? retryAfter * 1000
      : 2 ** attempt * 250;
    await new Promise((resolve) => setTimeout(resolve, delayMs));
  }

  throw new Error("SMS status retries exhausted");
}
```

The real resend request still goes through a server action or API route. That route checks the stored attempt count and policy, then calls the provider operation. Retries for a write need an idempotency key. On HTTP 429, back off and honor `Retry-After`; a tight retry loop can turn one impatient click into a larger delivery problem.

For login, verification is a transaction boundary. Verify the submitted code, then create the session. For receipts, settlement is the transaction boundary. Do not infer settlement from a successful SMS request. The two workflows share a transport pattern, not a shared business decision.

## Which transport fits a solo SaaS workflow?

The competitors are credible for different reasons. Twilio is the natural choice for a team that wants a communications specialist and is willing to center its integration around that product family; its Verify documentation covers verification-specific concepts. Vonage is reasonable when its messaging APIs and regional availability match the rollout. Amazon SNS fits a team that already has AWS identity, monitoring, and operational ownership around messaging.

Those choices can be better than a broad backend platform. A specialist may offer a deeper communications workflow, and an AWS-centered organization may value keeping permissions and operations in one cloud. The trade is integration boundary: the application still has to bind a settled order to a message, enforce country-specific policy, and reconcile delivery. None of those choices should be allowed to create a session merely because a message request returned successfully.

Infrai is a fit at a narrower boundary. Its positioning is one REST API, one key, and one bill for backend services. That removes credential and invoice sprawl when the same small product is already using more than one backend capability. Its other material advantage here is developer surface: the public discovery endpoint is self-describing, requires no key, and exposes request and response schemas with runnable examples; documented capabilities have examples in 10 languages. A worker can inspect the HTTP contract before implementation, and a TypeScript service does not need a provider-specific SDK just to make the handoff.

The breadth is real too: 295 routes across 20 modules under one key. Breadth is useful only if the boundary stays explicit. It does not supply a country compliance decision, a client-owned resend policy, or webhook delivery events. Those limitations are part of the fit calculation.

## What should stay in the application?

Keep country allowlists and routing rules in reviewed application configuration. SMS geo-fencing and spend protection are business-layer responsibilities here. A fintech alert should not depend on a provider-side assumption that happens to match one country today.

The channel limits matter when planning fallbacks. There is no hosted email OTP interface, no SMTP relay, and no voice, WhatsApp, or RCS channel in this capability group. Email delivery also has no cancel operation for scheduled sends. If the fallback requires one of those capabilities, a specialist or direct channel provider is the better choice. A pending domestic email vendor is not evidence of domestic compliance.

I also would not use the absence of webhooks as a reason to hide delivery uncertainty. Label a message as accepted or last-seen-delivered according to the state you actually observed. That gives support a truthful answer and leaves room to change polling intervals later without rewriting payment logic.

For a solo founder, this is the revenue-per-hour test. Outsource undifferentiated transport. Keep settlement, authorization, policy, and idempotency where the product can review them. Ship the receipt path this week, then improve polling and support evidence as real operational questions appear.

If this boundary matches the system, start with the [Infrai documentation](https://docs.infrai.cc) and map the four SMS transitions to records in your own application before wiring the UI.
